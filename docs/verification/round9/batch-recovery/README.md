# 普通批量解压异常退出后继续

普通批次开始时登记方案，首次写入完整来源、原目标和覆盖策略。逐项派发前保存一条短记录。已派发或刚完成准入的归档都划入「已开始」，只有下一条记录或正常暂停确认的状态会标记为成功、取消或失败。重开后由用户明确继续未开始的项目。替换同名文件仍要确认，部分输出不会主动清理或重跑。

仍为一个被用户占用的续跑位置。该位置已有正常暂停或意外退出记录时，新批次仍能解压，任务面板提示本批未登记。如果新批次此时异常退出，已有记录保留。手动暂停的新批次沿用原来规则，可在成功保存时替换已显示的旧正常暂停记录。已有意外退出记录必须先处理或清除，新的普通停机会在本次会话保留自己的待续项。未知格式保留，已识别但有半写记录时只提供原字节备份入口，无法确认的项目不进入续跑。只有最后一项中断时仍显示原目标和检查提示，可主动清除该记录。

## 本机实测

通过真正的 Windows 11 x64 窗口在普通 NTFS 上复跑。以下是独立 Debug GUI b1d9b8bc，R8 加固包的 CLI、worker 与运行时保持字节一致。后续提交另补未登记时的活动任务提示。主线相同输入的基线脚本可独立重跑。[主线基线](../batch-forced-exit/README.md)

- 新批次在第二项处理中强退，重开显示两个未开始的归档。按返回保留既有同名文件，明确选择替换后才执行第三、四项。第一项及第二项已有部分文件、原包和其他目标逐文件保留。独立进程在活动期间无法打开同一排他记录，在重开前由其再次持锁时，真实界面也不会领取或启动任务。[新批次回执](fresh.json)
- 一个已正常登记的暂停批次先继续，在第三项已经处理时强退。重开只执行第四、第五项，保持自动重命名策略。强退前以及已确认的已有文件与其他来源保持。[旧暂停继续后强退](resumed.json)
- 在本轮私有日志末尾追加半条准入，模拟追加中断留下的记录。重开显示无法确认哪些项目尚未开始，实际备份字节完全一致，输出未变。这是受控残尾用例，单独区别于完整记录的真实强退。[残尾回执](partial.json)
- 在两项批次的最后一项已经处理中强退。重开显示中断卡，能读到上一项目标，只有查看和清除，没有续跑操作。文件保持。[最后一项](last.json)
- 旧版正常关窗时序、替换二次确认、锁占用、不可写配置和已知损坏备份也使用实物重跑。Rust 的普通读写用例覆盖写准入失败、只允许正确顺序和完全不改动尾部的保守结果。

单轮诊断中，登记往返 5.7 ms，三个逐项准入分别 2.6、1.5、1.6 ms。该读数包含 WebView IPC，候选和基线的总体延时应看独立配对。真实强退验证针对应用进程退出。断电、操作系统未能保存写入及故障磁盘没有完成等价验收。[内部耗时回执](timing.json)

使用基线 README 的命令验证精确候选时，加 `--expect-recovery`。加 `--scenario resumed`、`--scenario partial` 或 `--scenario last` 进入相应场景。每组需要自己的新输出目录。

### 登记时的写入成本

初次写入计划时，序列化器会把许多短片段分别交给文件。把这些字节合并写入后仍先刷新缓冲、同步文件，再替换记录；逐项派发前的同步也保持。对普通 NTFS 临时文件做了一次预热、七对交替，按实际传给文件的写调用计数。3、24、512 项分别从 194、1,202、24,626 次降至 1、1、10 次，计划内容和换行逐字节相同。512 项的写入及同步中位从 43.35 ms 降至 0.82 ms。此计时来自独立序列化实验，不能推算整个批次的耗时。另在产品原生测试中登记 512 项、派发第一项后释放句柄重开，已开始项及余下 511 项全部核对。[七对原始数据](header-write-samples.json)

复跑时新建一个空的临时目录，在 [实验源码](header-write-probe/src/main.rs) 所在小包运行 `cargo run --locked --release -- <空目录>`。每一对保留两份输出以便检查。环境为 Windows 11 x64 26300、Ryzen 7 9800X3D、48 GiB、NTFS，保留系统缓存。
