# 已有 ZIP 在目标卷空间不足时的更新和重试

在一次性 Windows x64 的独占 96 MiB NTFS 虚拟磁盘上，运行第二轮便携源码的托管加固构建。此次使用包内 CLI 的常规 `add` 同时替换已有成员并加入一个不可压缩的 16 MiB 文件。源输入与系统临时目录位于另一卷，原 ZIP、无关文件和更新的私有暂存目录位于被测卷。[首次实跑](https://github.com/qing-yi-5427/qing-zip/actions/runs/45124377544)

| 操作开始时可用空间 | 失败阶段与数据保全 | 移除测试填充后的重试 |
| --- | --- | --- |
| 0 B | 创建私有暂存目录时返回 Windows 错误 112。原 ZIP 整体、两个原成员、两个输入和同目录无关文件的 SHA-256 均与操作前一致。 | 可用空间恢复至 83,726,336 B。同一命令完成，原有成员保留、选定成员替换、新成员加入。 |
| 6,291,456 B | 引擎报告更新进度后返回磁盘空间不足。相同的哈希和目录清单均保持，已有目录中没有未发布的临时文件。 | 可用空间恢复至 65,892,352 B。同一命令完成，三个成员经 Python 的 ZIP 读取器逐个解码并核对 SHA-256。 |

两次失败均返回 CLI 退出码 1，两次重试均返回 0。VHD 在作业结束时已卸载并移除。第二个用例记录的是非零起始空间及引擎错误，未计量报错时暂存文件已写入的字节数。嵌套编辑写回需要独立验证。

完整回执在工作流附件 `zip-disk-capacity-update` 的 `isolated-vhd.json` 和 `zip-space-receipt.json`。托管便携包 SHA-256 为 `c11730874d507890aaa64266563dc2a93c8d9da2c14bc64109605d435f96b98d`，产品源码为 `b2bf9f3f4eaddcbfefd3144ad0fdb8769fa1824b`。[包构建](https://github.com/qing-yi-5427/qing-zip/actions/runs/45118493619)

在包含本脚本的分支上手动运行 **Disposable Windows ZIP disk capacity**，选择 `trial=update`。原产物过期时可指定 `round2_build_run` 为相同产品提交的加固重建。涉及这些脚本的 PR 会自动运行两个历史组以及这组更新回归。
