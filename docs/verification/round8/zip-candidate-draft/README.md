# ZIP 更新完整候选回收草案

异常退出时，已经写完、尚未发布的 ZIP 候选可能留在归档旁的私有暂存目录。#53 在安装版 `c52c4ce` 复现三轮，每次重开和成功重试后仍留下一个 1,561,325 字节的候选。现有事务在原包移出公开路径后继续负责恢复原包。[基线与已移走原包的四项实测](../zip-commit/README.md)

在此草案中，程序仍持有候选的独占句柄和可撤销删除标记时，计算候选完整 BLAKE3 并同步保存 Windows 用户账户保护的回执，再把候选交给原有校验和提交。CLI 列表、完整性测试和直接重试通过仍公开的原包文件身份定位一个索引目录，最多查看 64 项索引，最多回收一个经验证的候选。索引位于当前用户的应用数据目录。归档旁的普通文件不会被枚举。

回收要求原包仍处于该公开名称，回执本身、原包、原包父目录、暂存目录、输出目录和候选的文件身份均相符。候选还需有一个实际链接，与记录的长度和完整摘要吻合。回收只标记锁定的候选句柄。损坏、未知版、被替换或正在占用的回执与对应文件继续保留。候选被外部改动、同名替换、无法读取或认领时也继续保留。每次更新具有独立回执，旧异常通常不会影响下一轮。超过 64 个保留项时，后续回执可能暂时落在本次查看范围以外。现有归档事务一旦写下非空记录即优先处理，原包成功恢复并截断记录后才允许继续候选回收。

正常结束后先处理阶段文件，再以句柄撤销当前作业的回执。原始创建者可尝试删除自己创建的空索引目录，非空目录由系统保留。反复执行可确认已不存在的候选并撤销准确回执。并发退出或强制退出的窄窗口仍可留下空索引目录或空暂存目录。无可用回执索引时，普通归档更新沿用原流程。启用此草案的范围是已有句柄式临时输出的普通顶层 ZIP 更新。现有事务意图已写入但公开原包仍在的极短阶段留给现有事务机制，仍可能保留候选；未登记旧产物、嵌套编辑、其他引擎路径及断电恢复各有原有边界。

## 实测

Windows 11 x64 build 26300，AMD Ryzen 7 9800X3D，普通本地 NTFS 文件。产品源码提交为 `6507242`。测试用 CLI SHA-256 为 `127e14510bf875b3dd624024abd3e3ef8a521633f97c3add22a30cf5dc1bccee`，worker 为 `46de592b0f628d795d7bb1143764107d67a4781f2c8c7ff3e4f2bcdb447468bd`。

- 在真实 CLI 对新增、删除、重命名分别验证四种情形。看见完整中央目录后关闭独立读句柄，强退发起进程。每种操作的列表、测试和直接重试均清除完整候选。应用数据目录不可用时，每种操作仍可重试完成，已退出作业的候选继续保留。原包在强退和重开阶段保持原 SHA-256，重试产物通过独立的成员级校验，来源和旁文件全部保全。 [新增回执](completed-add.jsonl) · [删除回执](completed-delete.jsonl) · [重命名回执](completed-rename.jsonl)
- 首版硬化 CLI `0be583c2…` 单独通过七项真实对照。精确登记的候选回收，未登记候选保留，原对象内容改动保留，同名替换保留，公开路径换为别的文件时保留，锁定中的候选保留并在释放后回收，并发重开只回收一次。原包或新占据公开名的独立文件和旁文件保持原样。 [七项原始记录](ownership-first-preview.jsonl)
- 11 项定向 Rust 回归覆盖活跃、重复回收、旧记录损坏后再次更新、复制同名回执、两种候选变化、旧原包移动、索引不可用以及既有事务交接。正常连续三次提交后索引目录为空。原有两项句柄归属和强退事务恢复用例也通过。真实 GUI 跨进程恢复与 ARM64 仍待实测。
- 无匹配索引时对实际 CLI 列包各预热一次，交替七对，缓存保持温暖。归档旁没有邻居时，中位数 62.533 → 64.816 ms，配对差中位数 +1.244 ms（−4.277 至 +12.808）。有 10,000 个普通邻居时，中位数 63.628 → 69.037 ms，配对差中位数 −1.240 ms（−6.623 至 +7.314）。辅助索引根目录存在，两个样本都没有匹配回执。 [逐轮列包结果](listing-final.json)

实际 CLI 把小文件加进 Store ZIP。基线为安装版 `c52c4ce`，实验组为首版硬化 CLI `0be583c2…`，两组各预热一次并交替五对，计时从发起 CLI 到退出。计时外独立核对每个成员及整个 ZIP，两组逐轮字节一致。每一对草案都更慢，两档独立中位数的差分别约 11.1% 和 11.8%。最终草案依然包含同一完整读取。128 MiB 普通文件、相同 256 KiB 分块和温暖缓存的独立哈希诊断显示 BLAKE3 中位数 24.073 ms（23.371–25.266），SHA-256 中位数 65.179 ms（64.315–65.683）。哈希诊断不包含产品校验与提交。 [逐轮 CLI 结果](stored-add-first-preview.json) · [逐轮哈希结果](hash-128mib.jsonl)

## 继续评审

草案暂缓合并和部署。小 ZIP 可优先验证能否在现有完整性校验已读取的原始缓冲区上计算摘要。候选尚在独占句柄下时通过该同一对象读取，先建立有效回执，再解除删除标记。必须在解除后继续通过已有发布语义绑定相同验证字节，关闭后按名字打开并比对文件 ID 无法排除同一文件被改写。先开放路径再计算完整摘要也会留出无可信回执的强退窗口。小包若在读取完整缓冲区后才决定移交原生校验，可复用这次读取的摘要，并继续运行原生完整性校验。

原生输出可以回写已写过的位置，原生解码也会跳到不同成员。直接按写入调用顺序哈希或拼接成员校验值，无法覆盖最终 ZIP 的全部原始字节。较大候选需要证明现有验证可复用同对象读取并涵盖所有原始字节，再测端到端性能。保持无证据即保留，避免用时间戳、长度或单个文件 ID 代替内容证明。

NTFS 变更序号方案可以复用仓库已有目录见证的校验思路，需要同卷文件身份、同一活动日志代次、未被裁剪的记录与明确的最终写入边界。微软文档说明按句柄读取的是最近已记录的序号，同一打开周期可合并变化，关闭也会写入记录，按文件查询返回的变更原因字段无效。候选仍保持删除状态的登记点与稍后的关闭是否能组成无歧义、无需管理员权限的见证，需要在一次性 Windows 环境用普通文件验证。日志不可用、代次变化、权限不够或观测不明确时继续保留。 [读取文件序号](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_read_file_usn_data) · [变更日志标识](https://learn.microsoft.com/en-us/windows/win32/fileio/using-the-change-journal-identifier) · [显式关闭记录](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_write_usn_close_record)

合并前用相同数据交替复测，确认普通大小的更新没有持续出现本次测到的额外整包读取回退，并复跑保全、已有恢复、真实桌面重开和两种 Windows 架构。#53 的原版验收脚本及记录仍可独立复现。本草案另有带用户目录隔离、回执计数和入口覆盖的脚本。

```powershell
python scripts/check-zip-candidate-receipts.py --cli <package>/obz.exe --action add --out add.jsonl
python scripts/check-zip-candidate-receipts.py --cli <package>/obz.exe --action rename --out rename.jsonl
python scripts/check-zip-candidate-receipts.py --cli <package>/obz.exe --action delete --out delete.jsonl
cargo test --manifest-path obz-rs/Cargo.toml --lib engine::edit_source::candidate_recovery::tests
```
